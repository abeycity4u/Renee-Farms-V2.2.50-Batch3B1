## Architecture traced — One fix, fit it all

- `lib/daily_population_sync.php::daily_population_sync_mortality` is the shared Layer/Broiler/Ruminant source-scoped mortality integration. It derives a desired canonical `mortality` projection from one durable Daily Record source; zero mortality requests desired `NULL` (removal). No page-local projection SQL should be introduced.
- `lib/production_population_projection.php::production_population_projection_sync` locks source cycles and V3 baselines, loads at most one active source movement, verifies source ownership, and **returns `unchanged` without new rows for an identical nonzero replay**. On a changed quantity it invokes `production_population_reverse_movement`, then records new source version `MAX(source_version)+1`, status `corrected`; a removed desired projection returns `removed` and leaves compensating reversal history. Repeated zero without an active projection returns `unchanged_empty`; reactivation after zero creates a new active movement with the next monotonic version. Old original rows and reversal rows stay immutable.
- `lib/production_population.php` owns the append-only `production_population_movements` movement and compensating `reversal` rows, checks canonical physical balance and implements exact source/version uniqueness and reversal-of-one-original idempotence.
- `lib/daily_population_continuity.php::daily_population_continuity_apply` requires caller PDO transaction, builds canonical pending mortality preview under locks before changing later openings and Layer laying rates. Caller route ordering is target source update → locked continuity → mortality projection (with Feed and Layer egg allocation layers where applicable), with caller commit/rollback.
- `lib/daily_population_boundary.php` aggregates effective active dated movements, excluding both reversed originals and compensating reversal rows, so repeated corrections do not stack mortality. Test must use *effective* physical balance, not raw sum of append-only audit rows.
